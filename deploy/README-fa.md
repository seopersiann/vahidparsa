# انتشار خودکار vahidparsa.com روی نت‌افراز

این پوشه یک دریافت‌کنندهٔ تغییرات GitHub با PHP CLI و Cron است. نیازی به FTP، SSH، وب‌هوک، IP ثابت، Composer، Node.js یا سرویس واسطه ندارد. پروژهٔ فعلی HTML/CSS/JavaScript استاتیک است؛ هیچ Build لازم نیست. ابزارهای این پوشه هیچ‌وقت داخل سایت منتشر نمی‌شوند. noindex فعلی سایت نیز تغییری نمی‌کند.

## وضعیت و محدودیت‌ها قبل از راه‌اندازی

کد و آزمایش‌ها آماده‌اند، اما روی حساب واقعی نت‌افراز نصب یا آزمایش نشده‌اند؛ هیچ فایل سایت فعلی حذف یا جایگزین نشده است. دسترسی به آن حساب در این پروژه وجود ندارد.

پیش‌نیازهای حساب:

- امکان Cron هر پنج دقیقه و اجرای PHP **CLI نسخهٔ ۸٫۱ یا بالاتر**؛ نسخهٔ ۸٫۲ یا جدیدتر توصیه می‌شود. نسخهٔ PHP وب و Cron ممکن است متفاوت باشند.
- افزونه‌های cURL، ZipArchive و OpenSSL، تابع flock و امکان خواندن/نوشتن فایل، تغییر نام فایل و ساخت پوشه.
- اتصال خروجی HTTPS پورت ۴۴۳ به `api.github.com` و `codeload.github.com`، همراه با گواهی‌های CA معتبر؛ بررسی TLS خاموش نمی‌شود.
- اجازهٔ دسترسی PHP به پوشه‌ای در Home، خارج از تمام document rootها. محدودیت open_basedir نباید این مسیر را مسدود کند.
- حداقل ۱۲۸ مگابایت حافظهٔ PHP و فضای خالی کافی برای آرشیو، نسخهٔ آزمایشی و پنج بکاپ تغییرات. محدودیت‌های پیش‌فرض: ZIP تا ۵۰ MiB، مجموع فایل‌های بازشده تا ۱۵۰ MiB، هر فایل تا ۱۶ MiB، حداکثر ۵۰۰۰ ورودی ZIP. برای این سایت فعلی کافی‌اند. فضای توصیه‌شدهٔ آزاد: حداقل ۲۰۰ مگابایت؛ در سایت بزرگ‌تر بیشتر.
- مجوز و زمان اجرای کافی برای دانلود و کپی فایل‌ها در Cron. قفل مانع هم‌پوشانی می‌شود، حتی اگر اجرای قبلی بیشتر از پنج دقیقه طول بکشد.

مسیر PHP و مجاز بودن فاصلهٔ پنج دقیقه را از پشتیبانی **همان پلن نت‌افراز** بپرسید. راهنمای نت‌افراز `/usr/local/bin/php` را نمونه می‌آورد، اما صریحاً می‌گوید این مسیر بین سرورها فرق می‌کند. این پروژه مسیر حساب شما را حدس نزده است.

اگر هر پیش‌نیاز برقرار نباشد، `check` یا `dry-run` خطا می‌دهند و نباید انتشار را فعال کنید. نبود SSH مانع نیست؛ همه مراحل اولیه با File Manager و Cron پنل انجام می‌شوند.

## ۱. بکاپ فعلی و مسیرها

ابتدا از File Manager یا بخش بکاپ DirectAdmin یک نسخهٔ کامل از سایت فعلی برای خود نگه دارید. این مرحله فقط تهیهٔ بکاپ است و نیازی به حذف یا جابه‌جایی سایت ندارد. بکاپ‌های بعدی ابزار فقط فایل‌های درگیر در انتشار را نگه می‌دارند؛ جای بکاپ کامل هاست، ایمیل و پایگاه داده را نمی‌گیرند.

در مثال‌ها `USERNAME` را با نام کاربری واقعی DirectAdmin و `/home/USERNAME` را با Home واقعی حساب جایگزین کنید. بعضی سرورها `/home2/USERNAME` دارند. مسیر واقعی را از File Manager/پشتیبانی بخوانید.

ساختار نصب:

```text
/home/USERNAME/
├── vahidparsa-deploy/           ← مجوز 0700، خارج از public_html و private_html
│   ├── deploy.php
│   ├── Publisher.php
│   ├── config.php              ← مجوز 0600؛ حاوی توکن
│   ├── cron.log                ← خروجی Cron؛ در Home خصوصی
│   └── data/                   ← خودکار ساخته می‌شود، 0700
│       ├── update.lock
│       ├── state.json
│       ├── plan.json
│       ├── deploy.log
│       ├── pending.json        ← فقط حین تراکنش یا پس از قطع ناگهانی
│       └── backups/
└── domains/vahidparsa.com/public_html/   ← سایت فعلی؛ در مرحله آزمایش دست‌نخورده
```

**هیچ‌کدام از فایل‌های این ابزار یا توکن را در public_html، private_html یا زیرپوشهٔ سایت قرار ندهید.** نام «private_html» در DirectAdmin لزوماً به معنای خارج از وب نیست.

## ۲. دقیقاً چه فایل‌هایی را آپلود کنیم؟

از پوشهٔ `deploy` این مخزن فقط این سه فایل را با **File Manager دایرکت‌ادمین** در `/home/USERNAME/vahidparsa-deploy/` آپلود کنید:

1. `deploy.php`
2. `Publisher.php`
3. `config.example.php` و سپس نام آن را در هاست به `config.php` تغییر دهید.

فایل‌های تست و این راهنما لازم نیست روی هاست باشند. برای نصب ابزار، هیچ فایلی در public_html آپلود نکنید. پوشهٔ `vahidparsa-deploy` را 0700 و `config.php` را 0600 کنید. اسکریپت‌ها می‌توانند 0600 باشند چون با همان کاربر PHP CLI خوانده می‌شوند؛ مجوز اجرایی 0755 برای خود فایل PHP لازم نیست.

## ۳. ساخت توکن فقط خواندنی GitHub

برای مخزن عمومی، فیلد token می‌تواند خالی باشد. برای مخزن خصوصی:

1. در GitHub وارد Settings حساب شوید؛ سپس Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token.
2. Resource owner را حساب صاحب مخزن، و Repository access را **Only select repositories** انتخاب کنید. فقط `seopersiann/vahidparsa` را انتخاب کنید.
3. Repository permissions → **Contents: Read-only**. Metadata: Read-only معمولاً خودکار است. هیچ دسترسی Write، Administration، Workflows یا دسترسی همهٔ مخازن لازم نیست.
4. تاریخ انقضای مناسب تعیین کنید. در سازمان‌ها ممکن است تأیید مالک/مدیر یا الزامات دسترسی سازمان لازم باشد.
5. توکن را فقط در `config.php` خصوصی هاست بگذارید. آن را داخل GitHub، چت، HTML، URL، فرمان Cron یا لاگ ننویسید.

توکن منقضی/باطل شود، دریافت تغییرات متوقف می‌شود و سایت قبلی باقی می‌ماند. تمدید/چرخش توکن و تأمین فضای هاست نگهداری دوره‌ای لازم‌اند؛ خود انتشارها پس از نصب دستی نیستند.

## ۴. ویرایش config.php

نمونهٔ حداقلی را به این شکل تکمیل کنید و بقیهٔ گزینه‌های فایل نمونه را نگه دارید:

```php
'enabled' => false,
'repository' => 'seopersiann/vahidparsa',
'branch' => 'main',
'token' => 'YOUR_FINE_GRAINED_READ_ONLY_TOKEN',
'target' => '/home/USERNAME/domains/vahidparsa.com/public_html',
'storage' => '/home/USERNAME/vahidparsa-deploy/data',
'keep_backups' => 5,
```

`enabled` در این مرحله **false** بماند. مسیر target باید پوشهٔ واقعی و موجود سایت باشد. data باید جدا از target باشد و داخل آن یا والد آن نباشد.

## ۵. آزمایش اولیه بدون تغییر سایت

DirectAdmin → Advanced Features / تنظیمات پیشرفته → **Cron Jobs** → افزودن.

زمان‌بندی:

| فیلد | مقدار |
|---|---|
| Minute | `*/5` |
| Hour | `*` |
| Day of Month | `*` |
| Month | `*` |
| Day of Week | `*` |

در **Command** ابتدا دستور زیر را قرار دهید. در نمونه، `/usr/local/bin/php` فقط نمونهٔ مستند نت‌افراز است؛ مسیر تأییدشدهٔ PHP CLI حساب خودتان را به‌جایش بگذارید:

```sh
/usr/local/bin/php /home/USERNAME/vahidparsa-deploy/deploy.php --config=/home/USERNAME/vahidparsa-deploy/config.php check > /home/USERNAME/vahidparsa-deploy/cron.log 2>&1
```

فقط متن دستور را در Command بگذارید؛ پنج فیلد زمان‌بندی را دوباره اول Command ننویسید. پس از اجرای Cron، `cron.log` را از File Manager باز کنید. باید `check_passed` ببینید. این دستور نسخهٔ PHP، افزونه‌ها، مجوزها و دریافت SHA از GitHub را بررسی می‌کند و سایت را تغییر نمی‌دهد. در صورت خطا، انتشار را فعال نکنید. `check` امکان اتصال به api را می‌سنجد؛ اتصال codeload و ZIP در dry-run سنجیده می‌شوند.

سپس فقط واژهٔ `check` را در همان Cron به `dry-run` عوض کنید:

```sh
/usr/local/bin/php /home/USERNAME/vahidparsa-deploy/deploy.php --config=/home/USERNAME/vahidparsa-deploy/config.php dry-run > /home/USERNAME/vahidparsa-deploy/cron.log 2>&1
```

پس از اجرا باید این دو رویداد را ببینید:

```text
dry_run_passed
no_live_changes
```

در `data/plan.json` باید `rehearsal_passed: true` و فهرست مسیرهای تغییر وجود داشته باشد؛ مقدار `null` به معنی حذف فایلِ قبلاً مدیریت‌شده است. در نصب اول، ابزار هیچ فایل مدیریت‌نشده‌ای را حذف نمی‌کند. dry-run فایل‌های نسخهٔ GitHub را دانلود، بررسی و در پوشهٔ آزمایشی خصوصی منتشر می‌کند، سپس همان نسخهٔ آزمایشی را rollback و نتیجه را کنترل می‌کند. محتوای public_html و state زنده را تغییر نمی‌دهد.

قبل از ادامه مسیر target و فهرست plan را بخوانید. اگر مسیر یا تغییرها درست نیستند، config را اصلاح کنید و dry-run را دوباره اجرا کنید. Cron آزمایشی را ماه‌ها فعال رها نکنید؛ هر بار آرشیو را دوباره دریافت می‌کند.

## ۶. فعال‌سازی پس از آزمایش موفق

فقط پس از مشاهدهٔ موفقیت dry-run و بازبینی plan:

1. در config.php مقدار `enabled` را به `true` تغییر دهید.
2. Command همان Cron را به `run` تغییر دهید:

```sh
/usr/local/bin/php /home/USERNAME/vahidparsa-deploy/deploy.php --config=/home/USERNAME/vahidparsa-deploy/config.php run > /home/USERNAME/vahidparsa-deploy/cron.log 2>&1
```

زمان‌بندی همچنان `*/5 * * * *` است. اگر پنل یک خط کامل crontab می‌خواهد، معادل آن:

```cron
*/5 * * * * /usr/local/bin/php /home/USERNAME/vahidparsa-deploy/deploy.php --config=/home/USERNAME/vahidparsa-deploy/config.php run > /home/USERNAME/vahidparsa-deploy/cron.log 2>&1
```

دیگر نیازی به آپلود فایل‌های سایت نیست. هر اجرا SHA شاخهٔ main را می‌خواند. اگر تغییر نکرده باشد، آرشیو دانلود نمی‌شود. اگر تغییر کرده باشد، دریافت دقیق همان commit، کنترل آرشیو، آزمایش خصوصی انتشار و rollback، تهیهٔ بکاپ و سپس انتشار انجام می‌شوند. هر نسخهٔ تازه هم باید از آزمایش خصوصی عبور کند.

بعد از اولین `published`، صفحهٔ اصلی، درباره من، یک مقاله، عکس‌ها و فونت را در دامنه واقعی باز کنید. از بین push تا انتشار معمولاً فاصله‌ای تا پنج دقیقه **به‌اضافهٔ زمان اجرا** وجود دارد. قطع اینترنت، توقف Cron یا محدودیت هاست می‌تواند این زمان را بیشتر کند.

اگر از قبل `index.php` یا `.htaccess` مخصوص وردپرس دارید، ممکن است وب‌سرور آن‌ها را بر index.html مقدم بداند؛ ابزار آن‌ها را حذف یا تغییر نمی‌دهد. `existing_index_php` در خروجی check این مورد را مشخص می‌کند. ترتیب صفحهٔ پیش‌فرض/مسیر‌دهی را فقط پس از dry-run موفق با پشتیبانی نت‌افراز بررسی و جداگانه تنظیم کنید.

## ۷. توقف، بازگشت و خطا

توقف امن: `enabled=false`. دستور `run` در این حالت فوراً با `paused_no_live_changes` خارج می‌شود. می‌توانید Cron را نیز غیرفعال کنید.

برای بازگرداندن آخرین انتشار موفق:

1. ابتدا `enabled=false` کنید.
2. Command را موقتاً به این دستور تغییر دهید:

```sh
/usr/local/bin/php /home/USERNAME/vahidparsa-deploy/deploy.php --config=/home/USERNAME/vahidparsa-deploy/config.php rollback > /home/USERNAME/vahidparsa-deploy/cron.log 2>&1
```

پس از رویداد `rollback`، Cron را غیرفعال کنید یا به `run` برگردانید؛ با enabled=false متوقف می‌ماند. دستور rollback را تکرارشونده رها نکنید، چون هر اجرای بعدی می‌تواند یک نسخهٔ دیگر عقب برگردد. برای اصلاح دائمی، commit مشکل‌دار را در GitHub برگردانید/اصلاح کنید، dry-run بگیرید و انتشار را دوباره فعال کنید؛ در غیر این صورت همان main مشکل‌دار دوباره منتشر می‌شود.

اگر PHP در میانهٔ انتشار قطع شود، pending.json باقی می‌ماند. `run` فعال در اجرای بعدی ابتدا نسخهٔ پیشین را بازیابی می‌کند و همان اجرا تمام می‌شود. اگر سیستم را متوقف کرده‌اید، با enabled=false دستور `recover` را به‌جای rollback اجرا کنید تا تراکنش نیمه‌تمام بازیابی شود. فایل pending.json را دستی حذف نکنید.

بازگشت قبل از هر تغییر، سالم بودن بکاپ و تضاد با ویرایش دستی را کنترل می‌کند. اگر فایلی پس از انتشار خارج از این سیستم ویرایش شده باشد، rollback به‌جای پاک کردن آن ویرایش متوقف می‌شود؛ لاگ را بررسی و تعارض را دستی رفع کنید. کمبود فضا، خرابی دیسک یا ممنوع شدن مجوز نوشتن می‌تواند خود بازیابی را هم متوقف کند؛ در آن وضعیت بکاپ خصوصی و journal برای بازیابی پس از رفع مشکل باقی می‌مانند.

فایل‌های گزارش:

- `cron.log`: خروجی آخرین اجرای Cron، با `>` بازنویسی می‌شود تا رشد نکند.
- `data/deploy.log`: تاریخچهٔ رویدادها با چرخش در حدود ۱ MiB؛ یک فایل قبلی نیز نگه داشته می‌شود.
- `data/state.json`: commit فعلی، فایل‌های مدیریت‌شده و شناسهٔ بکاپ بازگشت.
- `data/backups/ID/backup.json` و `files/`: محتوای قبلی فایل‌های تغییرکرده/حذف‌شده و ثبت فایل‌های تازه.

لاگ‌ها زمان UTC دارند. توکن، URL امضاشدهٔ آرشیو و پاسخ خام GitHub در آن‌ها ثبت نمی‌شوند.

## محافظت و حدود تضمین

- قفل flock در کل اجرا برقرار است؛ اجرای دوم با `locked_skip` خارج می‌شود.
- پیش از اولین تغییر زنده، بکاپ کاملِ تمام فایل‌های درگیر و journal ذخیره و کنترل می‌شوند.
- فایل‌ها جداگانه با rename اتمی جایگزین می‌شوند. انتشار چندفایلی در مجموع یک تراکنش کاملاً اتمی وب‌سرور نیست؛ در فاصلهٔ کوتاه کپی ممکن است فایل‌هایی از دو نسخه دیده شوند. بدون تغییر تنظیمات DocumentRoot یا symlink هاست اشتراکی، وعدهٔ انتشار تماماً اتمی داده نمی‌شود.
- ابزار فقط مسیرهای publish با پسوندهای ثابت و مجاز را می‌نویسد. PHP، dotfileها، تنظیمات و مسیرهای protect منتشر نمی‌شوند. برای فایل‌های حساس اضافی، protect را **پیش از فعال‌سازی** تکمیل کنید. حذف فقط برای فایل‌های قبلاً مدیریت‌شده انجام می‌شود؛ پوشه‌ها و فایل‌های دیگر پاک نمی‌شوند.
- ZIP از نظر مسیرهای خروج از پوشه، لینک نمادین، ورودی تکراری، حجم و فایل‌های خاص بررسی می‌شود. symlink در مسیر فایل‌های زنده نیز پذیرفته نمی‌شود.
- بکاپ‌ها خصوصی‌اند و حداقل دو، پیش‌فرض پنج بکاپ اخیر نگه داشته می‌شوند. پاک کردن دستی data/state.json سبب از دست رفتن سابقهٔ مدیریت فایل‌ها می‌شود؛ آن را حذف نکنید.
- ارتباط از هاست به GitHub برقرار می‌شود؛ ورودی شبکه، وب‌هوک، پورت باز یا IP ثابت لازم نیست.
- ابزارِ نصب‌شده خودش را از GitHub به‌روزرسانی نمی‌کند. فقط محتوای سایت خودکار است. تغییر نسخهٔ خود ابزار نیاز به جایگزینی همین فایل‌های خصوصی پس از آزمایش دارد.
- این نسخه برای سایت استاتیک فعلی است. اگر بعداً framework یا Build اضافه شد، نباید Node را بی‌اطلاع روی هاست اجرا کرد؛ باید خروجی استاتیک از پیش ساخته‌شده و فهرست انتشار متناسب در نظر گرفته شوند.

## آزمایش توسعه‌دهنده

```sh
php -l deploy/deploy.php
php -l deploy/Publisher.php
php deploy/tests/run.php
```

آزمایش‌ها مستقل از شبکه و فقط در پوشهٔ موقت هستند: اجرای هم‌زمان، dry-run بدون تغییر سایت، انتشار و حذف فایل مدیریت‌شده، حفظ تنظیمات هاست، مجوز پوشه‌های عمومی، بکاپ و rollback، خطای میانهٔ انتشار، بازیابی journal، traversal/symlink در ZIP، تغییر فایل stage و تعارض ویرایش خارجی.

دانلود واقعی از مخزن عمومی و آزمایش کامل روی سایت شبیه‌سازی‌شده نیز هنگام پیاده‌سازی انجام شد. دسترسی مخزن خصوصی با توکن واقعی کاربر و تنظیمات حساب نت‌افراز باید هنگام نصب با check و dry-run تأیید شوند.
